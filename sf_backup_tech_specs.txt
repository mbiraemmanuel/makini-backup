3. SALESFORCE API SPECIFICATIONS
--------------------------------------------------------------------------------

API Version
  - Target: v59.0 (Winter '24) or latest available in client org
  - Minimum supported: v52.0

Authentication — JWT Bearer Flow
  - Grant type:  urn:ietf:params:oauth:grant-type:jwt-bearer
  - Token endpoint (production): https://login.salesforce.com/services/oauth2/token
  - Token endpoint (sandbox):    https://test.salesforce.com/services/oauth2/token
  - Token lifetime: 3600 seconds (1 hour)
  - JWT expiry window: 300 seconds (5 minutes)
  - Algorithm: RS256
  - Key size: 2048-bit RSA minimum

Connected App Requirements
  - OAuth scopes required:
      api                              (Manage user data via APIs)
      refresh_token offline_access     (Perform requests at any time)
  - Use digital signatures: ENABLED
  - Certificate: X.509 self-signed, 365-day minimum validity
  - Permitted users: Admin approved users are pre-authorized
  - Callback URL: https://localhost (placeholder; not used in JWT flow)

Integration User Requirements
  - Profile: API Only (custom profile, no UI login)
  - License: Salesforce (full) or Integration (API-only license if available)
  - MFA exemption: required for JWT Bearer flow
  - Password never expires: ENABLED
  - Required object permissions: Read on all backed-up objects
  - Required system permissions:
      API Enabled
      View All Data (recommended for full backup)
      Manage Connected Apps (not required at runtime)

Bulk API 2.0 Specifications
  - Endpoint: /services/data/vXX.0/jobs/query
  - Job type: query
  - Content type: CSV
  - Concurrency mode: parallel (default)
  - Max concurrent jobs: 5 per org (Salesforce governor limit)
  - Max records per job: unlimited
  - Column delimiter: COMMA
  - Line ending: LF
  - Poll interval: 10 seconds
  - Poll timeout: 3600 seconds (1 hour)
  - Retry on: 503, 429, QUERY_TIMEOUT (up to 3 retries with exponential backoff)

REST API Endpoints Used
  - Object discovery:  GET /services/data/vXX.0/sobjects
  - Object describe:   GET /services/data/vXX.0/sobjects/{SObjectName}/describe
  - Metadata types:    GET /services/data/vXX.0/describe/metadataTypes
  - ContentVersion:    GET /services/data/vXX.0/sobjects/ContentVersion/{Id}/VersionData
  - Limits check:      GET /services/data/vXX.0/limits

Metadata API Specifications
  - Retrieval method: SFDX CLI (sf project retrieve start)
  - Output format: SFDX source format (human-readable, deployable)
  - Package.xml: dynamically generated per run
  - Max components per retrieve: 10,000 (chunked if exceeded)
  - Metadata types with chunking required:
      Report          (commonly exceeds 10k in large orgs)
      Dashboard
      EmailTemplate
      Document
  - SFDX CLI flags:
      --wait 60           (minutes before timeout)
      --target-org        (username or alias)
      --retrieve-dir      (local output path)
      --manifest          (path to package.xml)

Governor Limits to Respect
  - Bulk API v2 concurrent jobs: 5
  - REST API daily requests: 15,000 per license (standard) / 1,000,000 (unlimited)
  - Metadata retrieve size: 400 MB per request (uncompressed)
  - ContentVersion download: no explicit limit; stream directly, do not buffer in memory

6. DATA BACKUP — OBJECT SPECIFICATIONS
--------------------------------------------------------------------------------

Object Discovery Logic
  - Call GET /sobjects, iterate all sObject describe results
  - Include object if ALL of the following are true:
      queryable == true
      retrieveable == true
      createable OR updateable (exclude pure system/read-only objects)
  - Exclude if name matches any in the exclusion list (see below)

Default Exclusion List (system objects not useful to back up)
  - AggregateResult
  - ApexLog
  - AsyncApexJob
  - BackgroundOperation
  - BulkApiV2EventStore (internal)
  - CronJobDetail
  - CronTrigger
  - EntityDefinition
  - FieldDefinition
  - FlowVariableView
  - UserRecordAccess
  - Vote
  - LoginHistory (available via EventLogFile instead)
  - SetupAuditTrail (exported separately as a special case)

SOQL Export Query Template
  Full backup:
    SELECT {all_fields} FROM {SObjectName} ORDER BY Id

  Incremental backup:
    SELECT {all_fields} FROM {SObjectName}
    WHERE LastModifiedDate >= {since_timestamp}
    ORDER BY Id

  Note: Objects without LastModifiedDate (e.g., ContentDocumentLink)
        always run as full exports.

Field Handling Rules
  - Export ALL fields returned by describe (including formula, rollup, encrypted)
  - Encrypted fields: exported as masked values per org security settings
  - Long text area fields: exported as-is (Bulk API handles truncation at 32k chars)
  - Binary fields (base64): NOT exported via Bulk API; handled by file export module
  - Geolocation fields: exported as compound field (lat/lng as separate columns)
  - Polymorphic lookup fields (What, Who, Owner): export as Id + Type columns

CSV Output Specifications
  - Encoding: UTF-8 with BOM (ensures Excel compatibility)
  - Delimiter: comma
  - Line ending: CRLF (Windows-compatible)
  - Quote character: double-quote
  - Null values: empty string (no placeholder)
  - Boolean values: true / false (lowercase)
  - Date format: ISO 8601 (YYYY-MM-DDTHH:MM:SS.sssZ)
  - Filename: {SObjectName}.csv

8. FILE & ATTACHMENT BACKUP SPECIFICATIONS
--------------------------------------------------------------------------------

ContentVersion (Salesforce Files)
  - Query: SELECT Id, Title, FileExtension, ContentSize, VersionData,
           ContentDocumentId, CreatedDate, LastModifiedDate
           FROM ContentVersion WHERE IsLatest = true
  - Download endpoint: GET /sobjects/ContentVersion/{Id}/VersionData
  - Stream directly to Drive (do not buffer full file in memory)
  - Filename: {ContentDocumentId}_{Title}.{FileExtension}
  - Index file: content_version_index.csv (maps IDs to filenames)

Legacy Attachments
  - Query: SELECT Id, Name, ContentType, BodyLength, ParentId,
           CreatedDate FROM Attachment
  - Download endpoint: GET /sobjects/Attachment/{Id}/Body
  - Filename: {Id}_{Name}
  - Index file: attachment_index.csv

File Download Specifications
  - HTTP streaming: response.iter_content(chunk_size=10 * 1024 * 1024)
  - Resumable Drive upload for files > 5 MB
  - Max retries per file: 3
  - On repeated failure: log and skip; report in manifest
  - Parallel downloads: max 3 concurrent (respect SF API rate limits)

Storage Routing
  - Files < 10 GB total per run: upload to Google Drive
  - Files >= 10 GB total per run: route to GCS bucket
    Bucket naming: makini-sf-files-{client-slug}
    Storage class: NEARLINE (infrequent access, lower cost)

9. ERROR HANDLING & RETRY SPECIFICATIONS
--------------------------------------------------------------------------------

Retry Policy (using tenacity library)
  - Max attempts: 3
  - Wait strategy: exponential backoff
  - Initial wait: 5 seconds
  - Multiplier: 2x
  - Max wait: 120 seconds
  - Retry on HTTP status codes: 429, 500, 502, 503, 504
  - Retry on Salesforce error codes: QUERY_TIMEOUT, REQUEST_LIMIT_EXCEEDED

Non-retryable Errors (skip object, log, continue)
  - INSUFFICIENT_ACCESS_ON_CROSS_REFERENCE_ENTITY
  - INVALID_FIELD (field removed since last run)
  - ENTITY_IS_DELETED
  - MALFORMED_QUERY

Run Failure Behavior
  - Single object failure: log error, skip object, continue with remaining objects
  - Auth failure: abort entire run, send immediate alert
  - Drive upload failure: retry 3x, then abort run and alert
  - Metadata retrieval failure: log, alert, mark metadata status as error in manifest
  - Partial run: manifest marks overall status as "partial"

Alerting Thresholds
  - Immediate alert: auth failure, Drive unavailable, run abort
  - End-of-run alert (always): run summary with object count, errors, duration
  - Threshold alert: > 10% of objects fail in a single run

10. SECURITY SPECIFICATIONS
--------------------------------------------------------------------------------

RSA Key Pair Generation
  openssl genrsa -out private.pem 2048
  openssl req -new -x509 -key private.pem -out certificate.pem -days 365

  Protect private key:
    chmod 600 private.pem
    Store ONLY in GCP Secret Manager — never on disk in production

JWT Token Structure
  Header:  { "alg": "RS256" }
  Payload: {
    "iss": "{consumer_key}",
    "sub": "{integration_username}",
    "aud": "https://login.salesforce.com",
    "exp": {current_unix_time + 300}
  }
  Signature: RS256(base64url(header) + "." + base64url(payload), private_key)

Transport Security
  - All API calls: HTTPS / TLS 1.2 minimum
  - Certificate validation: enforced (no verify=False)
  - Drive API: OAuth2 via service account JSON (google-auth library)

Data at Rest
  - Google Drive: AES-256 encryption (Google-managed)
  - GCP Secret Manager: AES-256 encryption (Google-managed)
  - Cloud Run: ephemeral filesystem, wiped after job completion
  - Optional client-side encryption: GPG symmetric encryption of CSVs
    gpg --symmetric --cipher-algo AES256 --batch \
        --passphrase-file /path/to/passphrase Account.csv

Principle of Least Privilege
  - SF integration user: Read only on backed-up objects; no modify permissions
  - GCP service account: Editor on Drive folder only; no org-level Drive access
  - Cloud Run service account: Secret Accessor + Log Writer only
  - No shared credentials between client deployments

Audit Logging
  - All Cloud Run job executions logged to Cloud Logging
  - Log fields: run_id, client, status, object_count, error_count, duration
  - Log retention: 30 days (Cloud Logging default; extend if required by client)
  - Salesforce: all API calls logged in Salesforce Login History and API Usage

11. RETENTION & CLEANUP SPECIFICATIONS
--------------------------------------------------------------------------------

Retention Policy
  - Configurable per client in client config JSON
  - Default: 90 days
  - Starter tier: 30 days
  - Premium tier: 365 days

Cleanup Job
  - Runs at end of every backup job
  - Lists all dated folders in /SF Backups/
  - Deletes folders older than retention_days
  - Uses Drive API: files().delete(fileId=folder_id)
  - Logs deleted folders in manifest

Recovery Point Objective (RPO)
  - Data: 24 hours (nightly backup)
  - Metadata: 7 days (weekly backup)
  - Files: 7 days (weekly backup)

Recovery Time Objective (RTO) — Makini-managed restore
  - Data restore (single object): < 2 hours
  - Data restore (full org): 4–24 hours depending on org size
  - Metadata restore: < 4 hours
  - Target for Premium SLA: 4 hours end-to-end
